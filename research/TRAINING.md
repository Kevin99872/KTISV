## 一、框架選擇:為什麼不是 TensorFlow.NET

原本的構想是用 TensorFlow.NET 訓練,讓 .NET 端一路到底。**查證後確認這條路
在這台機器上走不通**,理由是硬體與版本的交集是空的:

| 事實 | 來源 |
|---|---|
| `SciSharp.TensorFlow.Redist-Windows-GPU` 最新版是 **2.10.3** | NuGet API 查詢 |
| TF 2.10 是最後一個支援 Windows 原生 GPU 的版本,其 CUDA 是 11.2 | TF 官方測試組態表 |
| 本機 GPU 是 RTX 1000 Ada,運算能力 **sm_89** | 實測 `torch.cuda.get_device_properties` |
| sm_89 從 CUDA 11.8 才存在 | NVIDIA 架構支援表 |

也就是說 TF.NET 在 Windows 上只能吃 CPU。**實測**這代價有多大
(medium 預設,batch=4,6 秒片段):

| 預設 | GPU | CPU | 倍率 | 60k 步:GPU vs CPU |
|---|---|---|---|---|
| small (5.16 M) | 0.37 s/step | 7.32 s/step | 20× | 6.1 小時 vs **5 天** |
| medium (11.6 M) | 1.77 s/step | 20.88 s/step | 12× | 29.5 小時 vs **15 天** |

(GPU 那一欄是與 CPU 同時、同條件下量的,所以可以直接比倍率;
它的絕對值偏保守,原因見下一節的說明。)

除了速度,改用 TF.NET 還要放棄已經驗證過的模型、STFT 往返、指標與混音實作,
在一個訓練支援薄很多的框架上重寫一遍。

**採用的方案:PyTorch 訓練 → ONNX → C# 端用 ONNX Runtime 推論。**
.NET 仍然參與,但參與在它擅長的部分;而且 KTISV 之後不必再為這個模型
開 Python 子行程(現在的 demucs 是那樣跑的)。

> **關於 medium 的一個量測差異,值得記下來。** 同一組設定我量到
> 4.86 GB / 1.77 s/step,而 `tests/test_model.py` 量到 4.53 GB / 0.74 s/step。
> 差別在於當下 GPU 上還有別的東西:我量的時候桌面程式佔了約 3.0 GB,
> 測試跑的時候只佔約 1.1 GB。
>
> 兩個數字都是真的,結論是:**medium 的餘裕小到會被「你當下有沒有開瀏覽器」
> 左右**。6 GB 扣掉桌面本來就要的 1～3 GB,4.53 GB 的峰值有時候放得下、
> 有時候放不下,放不下時就溢出到系統記憶體、慢一個數量級。
>
> 所以建議先用 **small**(峰值 3.24 GB,實測 0.37 s/step):它在任何情況下
> 都有餘裕,先把資料與方法跑通。等確定要拚品質,再在關掉其他程式的前提下
> 換 medium。

## 二、訓練資料

### 2.1 現況

**沒有。** 這是唯一擋住「真正開始訓練」的東西,而且我沒辦法代為取得 ——
MIR-1K 與 MUSDB18-HQ 都在 Zenodo 上設為需要申請,要先接受授權條款。
(已查證:MIR-1K 的 `access_right = restricted`。)

完整調查見 **DATASETS.md**。這裡只講管線怎麼接。

### 2.2 為什麼只有混音不夠

監督式分離要的是 **(混音, 人聲, 伴奏)** 三元組。從影片網站抓的音檔只有混音 ——
那是模型的輸入,不是它要學的目標。這類音檔只能拿來主觀試聽,不能訓練。

### 2.3 資料管線的三個決定(`data.py`)

**① 切分要按「組」,不是按片段。**
MIR-1K 的 1000 個片段來自 110 首歌、19 位歌手。若隨機把片段丟進 train/val,
同一首歌的不同片段會同時出現在兩邊,驗證分數會漂亮得毫無意義 —— 模型早就
聽過那個歌手、那個伴奏、那個混音風格。所以預設**按歌手切**:驗證集裡的人,
模型完全沒聽過。這比按歌切更嚴格,而分離模型最該具備的能力正是
「換一個沒聽過的人也分得開」。

**② 人聲與伴奏要能隨機重新配對。**
同一段人聲永遠只配同一段伴奏,模型可以靠「認出這段伴奏」反推人聲,而不是
真的學會分離。拆開隨機配,組合數從 N 變 N²,而且逼模型只能靠聲學特徵判斷。
代價是配出來的組合音樂上不見得合理(調性、速度對不上),所以預設只有
一半的樣本這樣配(`--independent-prob 0.5`)。

**③ 驗證集必須固定。**
`MixtureDataset(deterministic=True)` 讓每個索引永遠產生同一個混音。
否則每次驗證都在不同的隨機題目上算分,分數升降分不清是模型變好還是題目變簡單。

### 2.4 已驗證的不變量

```
載入: 8 段 / 8 組 / 共 4.0 分鐘 @ 44100 Hz
訓練/驗證分組不重疊: True
可加性殘差 (mixture − vocals − accompaniment): 4.47e-08
驗證集可重現: True     訓練集有隨機性: True
混音峰值範圍 0.387–0.736   (未削波)
```

可加性那一行特別重要:`混音 = 人聲 + 伴奏` 是監督式訓練的前提,
一旦混音的縮放沒有同步套用到分軌上,正確答案本身就是錯的,而模型會
忠實地學會那個錯誤 —— 且訓練曲線一切正常,完全看不出來。

### 2.5 MIR-1K 的一個限制,先講在前面

MIR-1K 是 **16 kHz** 錄音。重取樣到 44.1 kHz 不會把 8 kHz 以上的內容變出來,
那個頻段在這批資料裡本來就是空的。也就是說:**只用 MIR-1K 訓練出來的模型,
對 8 kHz 以上完全沒有學習訊號。**

這不代表 MIR-1K 沒用 —— 它是驗證方法最快的路徑。但它代表兩件事:
(a) 評估時要知道高頻的表現不可信;(b) 要能用在 KTISV 的 48 kHz 引擎上,
最終一定得混入全頻帶的資料(MUSDB18-HQ 或 M4Singer × 伴奏)。

## 三、模型架構

完整說明見 MODELS.md 第三節與 `model.py` 的檔頭。這裡只補這一輪釐清的部分。

```
混音波形 → STFT → 幅度譜 → U-Net → 遮罩 ∈ [0,1]
                                       ↓
人聲 ← iSTFT ← 複數譜 × 遮罩 ←─────────┘
伴奏 = 混音 − 人聲(架構上保證可加)
```

| 預設 | 參數量 | 峰值 VRAM | 6 秒 batch=4 | 判定 |
|---|---|---|---|---|
| tiny | 0.83 M | 2.18–2.80 GB | 0.86 s/step | 餘裕大 |
| **small** | **5.16 M** | **3.02–3.24 GB** | **0.37–0.46 s/step** | ⭐ **建議起點** |
| medium | 11.60 M | 4.53–4.86 GB | 0.74–1.77 s/step | 可用但吃緊(見上一節) |
| large | 33.46 M | 6.26 GB | 12 s/step | ❌ 溢出到系統記憶體 |

> 範圍是兩次獨立量測的差距,差異來自當下 GPU 上還有多少別的東西。
> 這個表要連著讀:`large` 那行不是「慢一點」,是**慢 16 倍** ——
> 「跑得動」和「能訓練」是兩件事。

### 修正一個文件錯誤

MODELS.md 原本寫「只處理 16 kHz 以下(`max_bins=1024`),更高頻段的遮罩固定
為 0 —— 保守地全給伴奏」。**這是錯的**,實際算過:

```
n_fft=2048 → 完整 1025 bins,max_bins=1024 → 保留 1024 個
最高保留頻率 = 22028 Hz,被丟掉的只有 22028–22050 Hz 這一個 bin
```

`max_bins` 真正的用途是**讓頻率軸能被 2^depth = 32 整除**(1025 除不盡,
1024 除得盡)。它不是低通,模型控制的是幾乎整個頻帶。
`model.py` 與 MODELS.md 的敘述都已更正。

這個更正有實際影響:原本以為「高頻保守地全給伴奏」的行為並不存在,
所以**高頻若出問題,不會有這層保護** —— 而 2.5 節說的 MIR-1K 高頻無訊號,
正好會落在這個沒有保護的區域。兩件事合起來看才知道要提防什麼。

## 四、訓練設定

### 4.1 損失函數,以及一個容易多寫的項

模型輸出人聲,伴奏定義為 `混音 − 人聲`,而資料保證 `混音 = 人聲 + 伴奏`。所以:

```
|伴奏_估計 − 伴奏_真值| = |(混音 − 人聲_估計) − (混音 − 人聲_真值)|
                        = |人聲_真值 − 人聲_估計|
```

**波形域的伴奏損失和人聲損失是同一個數。** 兩個都加只是把損失乘二,不會給
模型任何額外訊息。很多實作會兩個都寫,那是白費的。這裡只算人聲那一項。

預設用「波形 L1 + 幅度譜 L1」:

- **波形 L1** —— 直接對應最終聽到的東西,而且隱含要求相位正確
- **幅度譜 L1** —— 波形 L1 對相位誤差過度敏感,單用它時模型會為了對齊相位
  而犧牲頻譜正確性;加一項幅度損失把注意力拉回「頻譜對不對」。
  幅度譜同樣做 `log1p` 壓縮,理由和模型輸入端一樣:不壓縮的話,少數高能量
  時頻點會主導損失,安靜段落幾乎沒有梯度。

### 4.2 其他設定

| 項目 | 值 | 理由 |
|---|---|---|
| 優化器 | AdamW, lr 3e-4 | 這類任務的常規起點 |
| 排程 | Cosine → 5% | 末期降 lr 對 SDR 有穩定的小幅幫助 |
| 梯度裁剪 | 5.0 | 遮罩逼近 0/1 時 sigmoid 會出現大梯度 |
| 混合精度 | bf16(`--amp`) | 指數範圍同 fp32,不需要 GradScaler |
| 片段長度 | 6 秒 | 短了學不到樂句結構,長了吃 VRAM |

`--amp` 用 bf16 而非 fp16 是刻意的:fp16 需要 GradScaler,而 scale 一旦
爆掉會安靜地跳過更新;bf16 的指數範圍和 fp32 相同,沒有這個問題。
autocast 不會碰 `torch.stft`,所以複數頻譜全程維持 fp32。

## 五、評估指標

### 5.1 用哪個

`metrics.py` 提供四個層次(SI-SDR / uSDR / cSDR / BSS Eval)。訓練時監控用
**SI-SDR**:最穩健、最快,而且對整體音量不敏感 —— 模型把輸出整體放大 1 dB
不該被算成變差。要跟公開排行榜比時才用 uSDR。

要診斷「模型是沒分乾淨還是分過頭」時用 BSS Eval:
SIR 低 = 殘留其他音源,SAR 低 = 產生了假訊號。這兩種失敗要用不同的方法修,
只看 SDR 分不出來。

### 5.2 一定要有的基準線

訓練腳本每次驗證都會同時算一個 **passthrough 基準**:直接把混音當成人聲的
SI-SDR。真正該看的數字是 `si_sdr_improvement = 模型 − 基準`。

沒有這條基準線,「人聲 SI-SDR 12 dB」是好是壞根本無從判斷 —— 如果混音本身
就有 11 dB(人聲很大聲的歌),那模型只貢獻了 1 dB。訓練開始前也會先量一次
未訓練模型的分數,作為對照。

## 六、目前的結果

### 6.1 管線煙霧測試(合成音源,300 步,tiny)

```
訓練前 SI-SDR: 人聲 4.68 dB / 不分離基準 4.68 dB
step 100:  loss 0.1548   驗證 17.61 dB  (比不分離好 +12.92 dB)
step 200:  loss 0.1291   驗證 18.42 dB  (比不分離好 +13.74 dB)
step 300:  loss 0.1241   驗證 18.67 dB  (比不分離好 +13.99 dB)
峰值 VRAM 2.80 GB
```

### 6.2 ⚠️ 這些數字**不是**品質結果

必須講清楚,因為它看起來很像成果:

1. **音源是合成的。** `make_testset.py` 產生的「人聲」是正弦諧波堆疊。
   它和真實歌聲的差距大到 —— MODELS.md 記錄過 —— **Demucs 對這類訊號輸出
   近乎靜音,它根本認不出那是人聲。** 合成音源上的 18.67 dB 只證明模型
   有能力擬合一個簡單得多的問題。
2. **驗證集只有 1 組。** 8 個片段切出去 1 個,統計上毫無意義。
3. **300 步。** 真正的訓練是這個的一兩百倍。

**這一節唯一能宣稱的是:資料進得去、損失會降、驗證算得出來、檢查點存得下、
記憶體在預算內。** 也就是管線是通的。品質要等真實資料。

### 6.3 ONNX 匯出(實測)

```
卷積版 STFT vs torch.stft      4.482e-05
卷積版 iSTFT 往返               4.172e-07
整個模型 vs PyTorch             3.874e-07
ONNX Runtime vs PyTorch         4.321e-07   ← 真正重要的那個
可加性 (人聲 + 伴奏 = 混音)      5.960e-08
```

`torch.stft` / `torch.istft` 匯不出 ONNX(複數型別;ONNX 有 STFT 運算子但
從來沒有 ISTFT),所以 `export.py` 把兩者改寫成卷積 —— STFT 就是一組固定的
DFT 濾波器,iSTFT 是轉置卷積加上窗能量正規化。都是純實數,ONNX 完全支援。

換來的好處:C# 端只要餵波形、拿波形,不必在 KTISV 裡實作 FFT,也不會出現
「兩邊的窗函數或正規化慣例對不上」這種不會崩潰、只會讓聲音悄悄變差的錯誤。

**匯出時踩到並修掉的一個坑:** U-Net 在上採樣尺寸對不上 skip 時會用
`F.interpolate` 硬湊,那個目標尺寸在匯出時會被**當成常數烙進圖裡**,換一個
輸入長度就在 Concat 節點炸掉(實測:第 3 軸 129 對不上 128)。
解法是把片段長度挑成「頻譜幀數剛好被 2^depth 整除」,那條分支就永遠不會
觸發。所以模型固定吃 **261632 取樣(5.933 秒)**,整首歌由 C# 端切塊、
重疊相加。這個限制已寫進 ONNX 檔的 metadata,不會和文件走散。

> 這個 bug 是「用 ONNX Runtime 真的跑一次」才抓到的 —— 前面三項
> PyTorch 內部的比對全都通過。跨引擎驗證不能省。

**已知的浪費:** 匯出檔 36.9 MB,其中 **33.6 MB 是 DFT 基底常數表**
(0.83 M 參數本身只有 3.3 MB)。功能正確但明顯可以優化,見第七節。

## 七、怎麼做才會更好

### 7.1 下一步(照順序,每一步都能單獨驗證)

| # | 動作 | 為什麼是這個順序 |
|---|---|---|
| 1 | **拿到 MIR-1K** | 唯一的硬阻塞。2.2 小時、華語卡拉 OK、左右聲道天然配對 |
| 2 | small 預設跑 20k 步 | 先確認「真的在學分離」而不是記憶。看 `si_sdr_improvement` 是否穩定為正 |
| 3 | 用**未見歌手**評估 | 已經內建(按歌手切)。若訓練分數高但驗證分數不動,就是記住了 |
| 4 | 加 MUSDB18-HQ | 補全頻帶與西洋曲風,並取得可與排行榜比較的數字 |
| 5 | 換 medium / 加長片段 | 只有在資料夠多時才值得 —— 資料少的時候放大模型只會過擬合得更快 |

### 7.2 架構層面(依「投入 vs 回報」排序)

**值得做:**

- **複數遮罩 / 相位估計。** 目前只預測幅度、沿用混音相位,這是這類架構的
  固有上限,人聲軌會有輕微相位殘影。改成預測複數比值遮罩(cIRM)是這條路
  上回報最高的一步,VRAM 成本相對溫和。
- **多解析度頻譜損失。** 現在只用單一 n_fft=2048。加上 512 / 1024 / 4096
  幾個尺度,能同時照顧暫態與低頻解析度,幾乎不增加 VRAM。
- **在混音上做資料增強而不只是人聲。** 目前 `augment_vocals` 只做極性反轉與
  左右交換(刻意不做音高/速度變換 —— 那會扭曲模型要學的諧波結構)。
  可以再加:隨機 EQ、隨機殘響(用 DATASETS.md 提到的 PaRIRset)、隨機編碼
  失真(mp3/aac)。KTISV 的實際輸入是 YouTube 的有損音訊,而訓練資料是
  無損的 —— 這個落差值得補。

**先別做:**

- **換波形域模型或加注意力。** 這是品質上限真正的天花板沒錯,但 MODELS.md
  的實測已經說明:`large`(33 M,純卷積)就已經溢出到系統記憶體、慢 8 倍。
  6 GB 這張卡上沒有空間。要走這條路得先換硬體,不是先改程式。
- **合奏(ensemble)。** 對推論成本乘以模型數,而 KTISV 是要在使用者機器上
  跑的桌面程式。

### 7.3 工程層面

- **縮小 ONNX 檔。** 33.6 MB 的 DFT 常數表可以改成在 C# 端生成(基底是
  確定性的 cos/sin,幾行就能算),或存成 fp16。以 medium 來說能把
  46 MB 級的檔案壓到十幾 MB。
- **C# 端的分塊推論。** 固定 5.933 秒的塊要做重疊相加,重疊區用交叉淡接,
  否則塊與塊的接縫會有可聽見的不連續。這是 KTISV 那邊要寫的部分。
- **量化。** ONNX Runtime 支援 int8 動態量化。對這種卷積模型通常掉不到
  0.5 dB,檔案小四倍、CPU 推論快兩三倍 —— 對桌面應用很划算,值得量一次。

### 7.4 現實的品質預期

再強調一次 MODELS.md 已經寫過的:**這個架構是 Spleeter 的同類**
(頻譜 U-Net + 幅度遮罩)。合理預期是接近 Spleeter,**明顯低於 htdemucs**,
遠低於 BS-RoFormer。

所以這件事的價值不在「贏過現成模型」,而在:

1. 能在 6 GB 上真正訓練完,整條路自己走過一遍
2. 可以針對**華語卡拉 OK**這個特定場域微調 —— 通用模型不會為你做這件事
3. ONNX 之後,KTISV 不必再開 Python 子行程

如果目標純粹是最好的分離品質,直接用 htdemucs 仍然是理性選擇。
而且如第 2 節與 DATASETS.md 所述,**現成的 htdemucs 是 MIT 且權重可再散布,
自訓模型在「能不能跟著 KTISV 一起發佈」這點上反而更麻煩。**
這個取捨值得在投入 30 GPU 小時之前想清楚。

## 八、怎麼跑

```bash
cd research
uv sync --extra torch --extra eval --extra onnx

# 0. 管線煙霧測試(不需要真實資料,約 5 分鐘)
python -m ktisv_research.make_testset data/synth --seconds 30
python -m ktisv_research.train --dataset folders --root data/synth \
    --preset tiny --steps 300 --steps-per-epoch 100 --out data/runs/smoke --amp

# 1. 真正的訓練(拿到 MIR-1K 之後)
python -m ktisv_research.train --dataset mir1k --root data/MIR-1K/Wavfile \
    --preset small --steps 20000 --batch-size 4 --amp --out data/runs/mir1k

# 2. 匯出給 C# 端(含 ONNX Runtime 逐點比對)
python -m ktisv_research.export data/runs/mir1k/best.pt --out data/models/vocals.onnx
```

訓練過程逐步寫進 `data/runs/<name>/log.jsonl`,每行一筆
(step / loss / lr / 各項 SI-SDR),可以直接讀來畫曲線。
