# KTISV — YouTube 人聲分離混音台

抓 YouTube 音源 → 人聲/伴奏分離 → 分兩路輸出:一路給自己的耳機,一路合併麥克風後送進
Discord(或任何吃麥克風的軟體)。附升 key / 降 key、兩組參數式 EQ(影片一組、麥克風一組,
頻率 / Q / 段數都可調)、可選的麥克風回音、全路徑電平表,以及可勾選的自我監聽。

```
                 ┌─ 分離 ─┐  ┌ 變調 ┐  ┌ 影片 EQ ┐
  YouTube 音源 ──┤        ├─▶│      ├─▶│         ├─▶ 音樂推桿 ┬▶ ×送耳機 ┐
                 └────────┘  └──────┘  └─────────┘            │          │
                                                              └▶ ×送虛擬 ┼▶ 虛擬音效卡
  麥克風 ─▶ 麥克風 EQ ─▶ 回音(可選)─▶ 麥克風推桿 ─┬─▶ ×送虛擬 ─────────┘  (→ Discord)
                                                    │
                                                    └─▶ ×監聽(可勾選)───▶ 耳機
```

## 架構

| 層 | 技術 | 位置 |
|---|---|---|
| 介面 | C# / Avalonia 12(net10.0) | `KTISV/` |
| 音訊引擎 | Python(numpy / scipy / sounddevice) | `engine/` |
| 兩者之間 | localhost TCP,JSON-lines + token 認證 | `engine/ktisv_engine/ipc.py` |

前端啟動時會自己把 `python -m ktisv_engine` 拉起來、從 stdout 讀出埠號與 token 再連上去,
關閉時一併收掉。你不需要手動啟動引擎。

### 專案結構

```
KTISV/            C# 前端(Avalonia)。這個 README 在這裡
├─ Views/         各分頁的 XAML:YouTube 搜尋 / 卡拉 OK / EQ / 其他設定
├─ ViewModels/    MVVM 的 VM 層,所有對引擎的指令都從這裡送出
├─ Services/      引擎行程管理、TCP 客戶端、參數批次送出、驅動安裝
└─ Controls/      自訂控制項(電平表、數值輸入框)

├─ ktisv_engine/
│  ├─ audio/      裝置列舉、串流開關、混音核心(engine.py 是心臟)
│  ├─ dsp/        即時訊號處理:EQ、變調、回音、延遲線、分離、電平表
│  ├─ media/      YouTube 下載、ffmpeg 解碼、歌詞、Demucs 包裝
│  ├─ ipc.py      JSON-lines 伺服器
```

## 安裝

### 1. Python 相依套件(必要)

推薦用 [uv](https://docs.astral.sh/uv/) —— 它會自動抓對的 Python 版本並建立隔離環境:

```bash
cd engine
uv sync
```

這會在 `engine/.venv` 建立一個釘在 Python 3.12 的環境(PyTorch 目前對 3.14 支援不完整,
釘在 3.12 才能把 Demucs 裝進同一個環境)。C# 前端會自動找到這個 `.venv`。

沒有 uv 也可以用傳統方式:

```bash
pip install -r engine/requirements.txt
```

裝好後驗證環境:

```bash
cd engine && uv run python -m ktisv_engine --selftest
```

`imageio-ffmpeg` 會附帶一份 ffmpeg,所以**不需要**另外安裝 ffmpeg。

### 1b. 產出可散布的整包(給別人用,不需要裝 Python / .NET)

一行搞定:

```bash
powershell -ExecutionPolicy Bypass -File publish.ps1
```

它會先用 PyInstaller 打包 Python 引擎,再把前端發佈成**單一自包含 exe**,並自動把引擎
帶進輸出的 `engine-bin\`。產物在:

```
KTISV\bin\Release\net10.0\win-x64\publish\
├─ KTISV.exe        ← 自包含,含 .NET runtime;雙擊即可執行
└─ engine-bin\      ← 內建的 Python 引擎;目標電腦不需要裝 Python
```

把整個 `publish\` 資料夾壓成 zip 就能給別人。對方解壓、雙擊 `KTISV.exe` 即可,
不需要 Python 也不需要 .NET。前端會**優先**使用 `engine-bin\` 裡的引擎,只有在開發樹
(沒有 engine-bin)才退回原始碼 + Python。

> 為什麼不是「單一個檔案」?`KTISV.exe` 本身已是單檔(把 .NET 與所有相依都塞進去了),
> 但 Python 引擎另外放在 `engine-bin\` 而非再塞進同一個 exe —— 那樣做會讓 exe 每次啟動
> 都得把上百 MB 解壓到暫存目錄,又慢又容易被防毒攔。一個資料夾、一個雙擊,對使用者
> 來說就是一個 App。

> 打包版不含 PyTorch(會多 2 GB),所以只有即時分離。需要 Demucs 的人,另外建一個裝了
> demucs 的環境,設定環境變數 `KTISV_DEMUCS_PYTHON` 指向其 `python.exe`。

只想打包引擎(不發佈前端)的話,單獨跑 `engine\build.ps1` 即可,產物在
`engine\dist\ktisv-engine\`。

### 2. 虛擬音效卡(要送給 Discord 的話必要)

Windows 沒有內建「把程式輸出變成麥克風」的功能,需要一張虛擬音效卡。
安裝 [VB-CABLE](https://vb-audio.com/Cable/)(免費)後重開機,裝置清單裡會出現
`CABLE Input` 與 `CABLE Output`。

接線方式:

| 位置 | 選什麼 |
|---|---|
| KTISV → 「虛擬麥克風」 | **CABLE Input** |
| Discord → 設定 → 語音與視訊 → 輸入裝置 | **CABLE Output** |
| KTISV → 「耳機」 | 你真正的耳機 |
| KTISV → 「麥克風」 | 你真正的麥克風 |

> **裝完一定要做:把 Windows 預設播放裝置改回耳機。**
> VB-CABLE 安裝後常常會把系統預設輸出搶成 `CABLE Input`。沒改回來的話,所有系統聲音
> (瀏覽器、遊戲、通知音)都會灌進這條線路讓對方聽到,而且你自己什麼都聽不到。
> 位置:設定 → 系統 → 音效 → 輸出。`test_loopback` 會檢查這一項。

> Discord 的**回音消除 / 噪音抑制**會把音樂當成噪音削掉,請在語音設定裡關掉它們,
> 否則對方聽到的歌會斷斷續續。

> 兩端取樣率要一致。在「音效 → 進階 → 裝置內容」把 `CABLE Input` 與 `CABLE Output`
> 的預設格式都設成 48000 Hz,和引擎一致,否則會破音或音調跑掉。

### 3. Demucs 高品質分離(選用)

即時模式不需要任何模型就能用。想要更乾淨的分離再裝這個。

PyTorch 對 Python 3.14 的支援還不完整,建議開一個 3.12 的獨立環境:

```bash
py -3.12 -m venv engine/.venv-demucs
engine\.venv-demucs\Scripts\python -m pip install -r engine/requirements-demucs.txt
```

放在 `engine/.venv-demucs` 會被自動偵測到。放別處的話設定環境變數
`KTISV_DEMUCS_PYTHON` 指向那個 `python.exe`。裝好後在 UI 上按「偵測」確認。

### 4. 執行

```bash
dotnet run --project KTISV/KTISV.csproj
```

## 使用流程

1. 右欄選好**耳機**、**虛擬麥克風**、以及中欄的**麥克風**,按「▶ 啟動音訊」。
2. 上方欄位輸入**歌名關鍵字**按 Enter,會列出候選清單,點一首就直接載入;
   也可以直接貼 YouTube 網址、或按「瀏覽…」選本機檔案。(輸入框會自動判斷是關鍵字、
   網址還是檔案路徑。)
3. 左欄勾「剝離人聲」或「剝離伴奏」。
4. 唱不上去就按 **♭ / ♯** 調 key —— 只動音樂,不動你的聲音。
5. 想先確認自己的聲音,勾「聆聽自己的聲音」—— 這只會送到耳機,不影響 Discord 那一路。
   想要卡拉 OK 那種尾音,在麥克風欄勾「回音」。
6. 用各路推桿調平衡。**若聽到破音,先把「總輸出」拉低,而不是把各路推桿拉高。**
7. 對方覺得你的歌聲跟音樂沒對上,調「DC 延遲」(或直接按「套用建議值」)。

各功能的細節與取捨在下面幾節;EQ 在獨立的「EQ 調整」分頁。

### 耳返(監聽自己)與延遲

「聆聽自己的聲音」是耳返:你的麥克風經過 EQ 與推桿後直接送回耳機,**不會**進虛擬麥克風,
所以對方不會聽到兩份你的聲音。這條路走的是本程式自己開的裝置,不需要 Windows 的
應用程式輸出路由。

耳返能不能用只看延遲。UI 會即時顯示實測值:

| 延遲 | 感受 |
|---|---|
| < 10 ms | 察覺不到 |
| 10–20 ms | 唱歌沒問題 |
| 20–30 ms | 明顯,講話會有點怪 |
| > 30 ms | 會干擾發聲 |

延遲由三段組成:麥克風輸入緩衝 + 跨時脈環形緩衝 + 耳機輸出緩衝。中間的 DSP(分離、EQ、
混音)是零延遲的 —— 逐 block 處理,沒有前瞻。環形緩衝會自動修剪到只留一個 block 的餘裕。

剩下兩段由驅動與 WASAPI 模式決定,是延遲的大宗。**開「WASAPI 獨佔模式」是最有效的手段**,
在開發機上實測從 51.5 ms 降到 13.2 ms。代價是這些裝置會被本程式獨佔,其他程式(包含
Discord 自己的提示音)發不出聲音。不支援獨佔的裝置會自動退回共享模式並在 UI 顯示原因。

「緩衝大小」也會影響延遲,但不是越小越好 —— 太小會掉幀(xrun)。用
`python -m tests.test_latency` 可以掃出你這台機器上不掉幀的最低組合。

### 升 key / 降 key

半音為單位,上下各一個八度。**只動音樂,不動你的聲音** —— 目的是讓歌配合你的音域,
而不是把你的聲音改掉。速度完全不變。

單純重新取樣沒有用:放快 12% 音高確實升了兩個半音,但整首歌也快了 12%。所以拆成兩步 ——
相位聲碼器把訊號拉長 r 倍(音高不動),再以 r 倍速重新取樣縮回原長度(音高跟著 × r)。
兩步用同一個有理數,長度精確守恆。

| | |
|---|---|
| 音高誤差 | < 2 音分(人耳分辨的極限約 5–10 音分) |
| 速度誤差 | 0 ms |
| 延遲 | 約 41 ms,只加在音樂那一路 |
| CPU | 平均約 7% 的回呼預算,尖峰(FFT 那一幀)在 128 取樣下約 30% |

**原調時整條旁通** —— 沒有延遲也沒有 CPU 成本,所以不用時完全不必在意上面那些數字。

延遲不會影響對方聽到的對拍:音樂在耳機與虛擬麥克風兩路上延後同樣的量,你跟著晚唱,
兩者的相對關係不變,「DC 延遲」的建議值也不用改。但若你把緩衝開到最小(32 / 64 取樣)
又同時開變調,尖峰可能吃掉大半預算 —— 看狀態列的 xrun 數字,會跳就把緩衝調大一級。

超過 ±5 個半音之後相位聲碼器的假象會開始明顯,鼓和鈸最先聽得出來。

### 麥克風回音(ECHO)

卡拉 OK 機上那顆旋鈕,預設關閉 —— 唱歌好聽,講話會變得難聽懂。它接在麥克風 EQ 之後、
兩路分岔之前,所以你的耳返與對方聽到的是同一份效果。

| 參數 | 作用 |
|---|---|
| 回音時間 | 每一次重複相隔多久(20–1000 ms) |
| 重複次數 | 回授量。越高尾巴拖越長,90% 已經接近不會停 |
| 回音量 | 混進去多少。乾訊號不會被減弱,只是疊上去 |
| 高頻衰減 | 回授路徑上的低通。每次重複都比前一次暗一點,像真實空間;調 0 會變成金屬罐般的重複 |

回音不會增加耳返延遲 —— 原本的乾訊號照樣即時通過,疊上去的只是它自己的歷史。

### EQ

兩組獨立的參數式 EQ(影片 / 麥克風),預設各 10 段。每一段的**中心頻率**與 **Q** 都能直接
輸入(打完按 Enter 或點到別處才送出,可以寫「1.5k」這種寫法),也可以隨時**新增或刪除**
頻段,最多 24 段。

最左與最右那兩段會自動變成 shelf(從轉折點起整片抬升或壓低),中間各段是 peaking
(只動那一小塊)。Q 在 peaking 上代表頻寬,在 shelf 上代表轉折斜率。

預設集(人聲 / 電話 / 微笑曲線)存的是一條「頻率 → 增益」的曲線,套用時依每一段目前的
頻率取值,所以改過頻段配置之後仍然套得準。

增刪頻段時,留下來的頻段會把自己的濾波器狀態帶到新位置,只有新來的那一段從零開始 ——
所以可以邊播邊改,不會爆音。

### 兩個分離引擎的取捨

| | 即時中央消除 | Demucs |
|---|---|---|
| 延遲 | 零,可即時調整參數 | 要先跑完整首歌(CPU 約數分鐘) |
| 相依 | 無 | PyTorch(約 2 GB) |
| 去人聲品質 | 好 —— 實測把置中人聲壓下 27 dB,同時保住貝斯與大鼓 | 很好 |
| 取人聲品質 | 普通 —— 只能把左右分離的樂器壓掉約 6 dB | 很好 |

即時模式的原理是 mid/side 相消:主唱通常擺在正中央,`(L−R)` 就能把它消掉。代價是**所有**
置中的東西都會一起消失,所以用「保留低頻 / 保留高頻」把貝斯、大鼓、鈸這些置中樂器留下來。
硬左右分離的樂器則必然會少掉一半能量(−6 dB),這是這個演算法的固有代價,不是設定問題。
要乾淨的人聲軌就得用 Demucs。

## 測試

### 引擎(`engine/`)

```bash
cd engine
python -m tests.test_dsp        # 離線 DSP:環形緩衝、EQ、變調、回音、分離、混音路由
python -m tests.test_ipc        # 端對端:啟動真的引擎行程,走一輪所有指令
python -m tests.test_devices    # 實體裝置:真的開 WASAPI 串流(全程靜音)
python -m tests.test_loopback   # VB-CABLE 回送:從 CABLE Output 錄回來驗證對端收到什麼
python -m tests.test_latency    # 耳返延遲:拆解各段延遲,掃描 block 大小與獨佔模式
```

`test_dsp` 不開任何音訊裝置,所以隨時可以跑;它涵蓋每一個 DSP 元件,包括
「變調不改變速度」「增刪 EQ 頻段不爆音」「回音關閉後尾音清乾淨」這類
壞掉不會報錯、只會讓聲音悄悄變差的性質。

`test_devices` 沒有虛擬音效卡時會改用第二個實體輸出來驗證雙路架構。

`test_loopback` 是最接近真實情境的驗證:它只開虛擬音效卡那一路(所以你聽不到聲音),
把測試訊號送進 `CABLE Input`,再從 `CABLE Output`(也就是 Discord 要選的那個裝置)錄回來,
確認訊號有穿透、勾選框有生效、推桿刻度準確。沒裝 VB-CABLE 時會自動跳過。

### 前端(`KTISV/`)

```bash
dotnet build KTISV/KTISV.csproj
```

XAML 用編譯期繫結(`AvaloniaUseCompiledBindingsByDefault`),所以繫結路徑打錯
會**在建置時**就報錯,而不是執行時才變成空白畫面。建置通過本身就是一層驗證。

## 人聲分離模型(`research/`)

專案內建的即時分離是 mid/side 相消(零延遲、無模型),高品質選項是外部的
Demucs。`research/` 是第三條路:**自己訓練一個輕量的頻譜 U-Net**,目標是能在
6 GB VRAM 上訓練完,並針對華語卡拉 OK 這個場域微調。

訓練用 PyTorch(GPU),訓練完匯出 **ONNX** 給 C# 端的 ONNX Runtime 推論 ——
這樣 KTISV 之後不必為這個模型再開 Python 子行程。

| 文件 | 內容 |
|---|---|
| **`research/MODELS.md`** | 現成模型(Demucs / BS-RoFormer / Spleeter…)比較,與本專案架構的選型理由 |
| **`research/DATASETS.md`** | 語料調查:哪裡拿得到、授權能不能商用、對這個專案合不合適 |
| **`research/TRAINING.md`** | 訓練管線、損失函數、評估指標、實測結果與改進路線 |

**目前狀態:管線全部完成並通過測試,但還沒有訓練資料** —— MIR-1K 與
MUSDB18-HQ 都需要先向 Zenodo 申請並接受授權條款。細節見 `DATASETS.md`。

> ⚠️ 授權提醒:公開的分離語料幾乎都是**非商業 / 學術用途**。KTISV 目前用的
> htdemucs 是 MIT 且權重可再散布 —— 就「能不能跟著程式一起發佈」而言,
> 自訓模型反而比現況更麻煩。投入前值得先想清楚,`DATASETS.md` 第〇節有詳述。

## 疑難排解

**「引擎啟動失敗」**
前端找不到 Python。設定環境變數 `KTISV_PYTHON` 指向你的 `python.exe`,或在 `engine/.venv`
建虛擬環境(會被自動偵測)。詳細錯誤在「記錄」分頁。

**Discord 那邊沒聲音**
確認 KTISV 的「虛擬麥克風」選的是 `CABLE Input`(不是 Output),Discord 的輸入選的是
`CABLE Output`。看 KTISV 的「虛擬麥克風輸出」電平表有沒有在動 —— 有動就代表 KTISV 這側正常,
問題在 Discord 的設定。要更明確的話跑 `python -m tests.test_loopback`,它會直接告訴你
對端到底收到什麼。

**自己的耳機突然什麼都聽不到 / 對方聽得到我的瀏覽器聲音**
Windows 預設播放裝置被 VB-CABLE 搶走了。設定 → 系統 → 音效 → 輸出,改回你的耳機。
KTISV 走的是自己選的裝置,不受這個設定影響,所以改回來不會影響本程式運作。

**破音 / 爆音**
輸出端有軟限幅,但輸入端過載救不回來。看哪一格電平表的削波指示(右側小方塊)在亮,
把該路的推桿拉下來。

**聲音卡頓、xrun 一直增加**
狀態列會顯示 CPU 佔用(相對於音訊 block 的時間預算)。超過 50% 就容易掉幀 ——
關掉 Demucs 分離改用即時模式,或關掉其他吃 CPU 的程式。

**開了變調之後才開始 xrun**
變調的成本是**尖峰**而非平均:大多數回呼不做事,輪到 FFT 的那一幀才一次算完。
128 取樣下那一幀約佔預算 30%,32 / 64 取樣下比例更高。把「緩衝大小」調大一級,
或改回原調(原調時整條旁通,零成本)。

**變調之後音樂聽起來悶悶的 / 鼓聲怪怪的**
相位聲碼器的固有假象,超過 ±5 個半音會開始明顯。這不是設定問題,
是這類演算法的代價 —— 盡量把調整幅度控制在 ±5 以內。

**回音聽起來像金屬罐**
「高頻衰減」調太低。真實空間的殘響每次反射都會損失高頻,調到 30–50% 才自然。

**EQ 的頻率或 Q 打了數字沒反應**
這兩個欄位是**離開欄位或按 Enter 才送出**的(逐字送出的話,想打「150」時
第一個字就會被夾成下限)。打完按 Enter,或點一下別的地方。

**回授嘯叫**
用喇叭而不是耳機時,關掉「聆聽自己的聲音」。

## 設定與快取

| 內容 | 位置 | 重開後會回來嗎 |
|---|---|---|
| 介面設定(語言、緩衝大小、獨佔模式、精靈狀態) | `%LOCALAPPDATA%\KTISV\ui-settings.json` | ✅ 會 |
| 引擎設定(推桿、EQ、延遲、回音…) | `%LOCALAPPDATA%\KTISV\settings.json` | ❌ **不會**,見下 |
| 下載的音訊 | `%LOCALAPPDATA%\KTISV\cache\downloads\` | — |
| Demucs 分離結果 | `%LOCALAPPDATA%\KTISV\cache\stems\` | — |

同一個網址第二次載入會直接用快取,不會重新下載或重跑 Demucs。快取可以隨時整個刪掉。

> **已知限制:「儲存設定」目前是單向的。** 按下去會把推桿、EQ 頻段、DC 延遲、
> 回音等參數寫進 `settings.json`,引擎那側也實作了讀取指令,但前端從來沒有
> 呼叫它 —— 所以重開程式後這些值會退回預設。
>
> 會跟著回來的只有 `ui-settings.json` 那幾項(語言、緩衝大小、獨佔模式),
> 那是前端自己存的、另一套機制。
>
> 檔案本身是完整且正確的,缺的只是啟動時載入那一步。
